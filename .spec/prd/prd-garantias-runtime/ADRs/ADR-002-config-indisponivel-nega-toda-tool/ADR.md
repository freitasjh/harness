# ADR-002 — Config indisponível nega toda tool call (fail-closed no dispatcher)

> Unidade de decisão: 1 ADR = 1 branch = 1 PR (merge humano).
> **PRD**: `prd-garantias-runtime` · **Seções implementadas**: §1 (problema), §6 (escopo P1-B), §8 (risco 1), §9 (RF-02, RF-06) · **RF fechado**: RF-02 (RF-06 no desenho) · **Decisão do owner**: §16 Q2 (2026-10-22) — "escopo do deny de config indisponível: **toda tool call** (fail-closed total); `HARNESS_GATES=off` permanece como a saída declarada". Este ADR registra o **como**; a decisão do owner não é re-decidida aqui.

- **Decisão**: o config é carregado **uma única vez, no dispatcher, antes do loop de gates**; a falha de carga vira `DenyError(DENY_CONFIG_UNAVAILABLE)` **lançada fora de `decide()`** — o `throw` é o único primitivo de deny (SPEC ADR-001) — de modo que **toda** tool call é negada, e não apenas as que passam por um gate que pede o config. O `reason` do deny é `config-unavailable` com `details.cause` **enumerado** (`config-missing` | `config-invalid-json` | `config-unreadable`) e **sem eco do path** (I10). O kill-switch `HARNESS_GATES=off` é avaliado **antes** do carregamento e permanece como a saída declarada.
- **Motivo**: hoje `runGatesShim` engole o erro de carga e segue com `config = null` (`gate.js:1182-1189`), e o `DenyError("config-unavailable")` só nasce *lazy*, dentro dos gates que pedem o config — âncora A (`gate.js:771`) e higiene (`gate.js:993`). `gatePiccoTask`, `gatePhaseAnchorB` e `gateHitlBatch` nunca pedem o config, então `task` passa: a garantia "config fail-closed" amarra-se ao detalhe de *quais* gates leram o config, e o PRD §13 registra que **qualquer gate novo que não leia config reabre o furo** — a garantia está na implementação, não no contrato. O desenho do dispatcher resolve a causa de forma, não por lista: o `throw` fora de `decide()` é o mesmo primitivo de deny do resto do runtime (`gate.js:161-177`), e o `catch` que hoje engole o erro some — o `DenyError` propaga para o runtime, que nega a tool call. O PRD §8 risco 1 (fail-closed total pode travar o agente) é endereçado por dois dispositivos já existentes no desenho: o kill-switch precede a carga e o `reason` é acionável (PRD §11: "o `reason` do deny **é** a interface").
- **Alternativas descartadas**:
  - (a) **Manter o fail-closed lazy e apenas corrigir a prosa** — fonte: https://owasp.org/Top10/A05_2021-Security_Misconfiguration/ (configuração ausente ou inconsistente é falha da configuração, não permissão implícita) — **descartada**: a garantia continua valendo só para os gates que leem o config; o furo continua aberto e nenhum gate novo pode ser escrito sem saber que precisa pedir o config.
  - (b) **Negar via um gate sintético que "nega tudo"** — fonte: https://owasp.org/Top10/A01_2021-Broken_Access_Control/ (a decisão de autorização falha fechada **no ponto de decisão**) — **descartada**: um gate sintético nega por exaustão de tool — toda tool nova, não mapeada, escaparia; e o gate competiria com `decide()`, que já é o ponto de decisão único.
  - (c) **Negar apenas nas tools que hoje pedem o config** (`write`/`edit`/`bash`) — fonte: https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final (controles de configuração: a falha de configuração deve ser explícita e consistente, não uma configuração mais permissiva por omissão) — **descartada**: é exatamente o estado medido hoje (P1-B: `task` ⇒ ALLOW; `write`/`edit`/`bash` ⇒ DENY `config-unavailable`); o owner decidiu fail-closed total (Q2).
  - (d) **Seguir com o último config bom (cache stale em disco/memória)** — fonte: https://12factor.net/build-release-run (config estritamente separada do código: um build/release/run com config diferente do validado é outra configuração) — **descartada**: "usar o config antigo" é **permitir com configuração não verificada** — o oposto de fail-closed — e introduz estado compartilhado entre processos.
- **depende-de**: ADR-001 (as duas decisões alteram o mesmo dispatcher: `ADR-001` muda a resolução de modo dentro do loop, `ADR-002` insere a carga do config antes dele; a ordem de merge 1 → 2 evita conflito no mesmo bloco)
- **Interface congelada**:
  1. Ordem no dispatcher `runGatesShim`: **(a)** kill-switch — `HARNESS_GATES=off` ⇒ retorno `{verdict:"allow", via:"kill-switch"}` **sem tocar o config**; **(b)** carga do config — uma única vez; **(c)** loop de gates. O `DenyError` da carga é lançado do dispatcher (fora de `decide()`) e propaga para o runtime, que nega a tool call.
  2. `loadConfigOrDeny(path)` (`gate.js:220-236`) permanece como **único** ponto de tradução loader → deny. `details.cause` passa a ser um enum **sem path**: `config-missing` | `config-invalid-json` | `config-unreadable` (hoje é `err?.code ?? "load-error"` — sempre `"load-error"`, porque o loader lança `Error` sem `code`, `config.mjs:13-27`). A mensagem do loader continua contendo "fail-closed" e o caminho **nunca** é ecoado no log nem no `reason` (I10, `gate.js:145-156`).
  3. Sonda de aceite: `runGatesShim` com `configPath` inexistente ⇒ **deny `config-unavailable`** para `task`, `write`, `edit` e `bash` (as 4 tools da métrica do PRD §5), com `details.cause` ∈ enum.
  4. `HARNESS_GATES=off` ⇒ **allow** em todas as tools, mesmo com config ausente ou inválido — o kill-switch precede a carga (item 1a).
  5. Os gates que hoje chamam `ensureConfig(ctx)` (`gate.js:771`, `gate.js:993`) passam a receber o config **já carregado** em `ctx.config`; `ensureConfig(ctx)` permanece com a mesma assinatura e o mesmo comportamento (`ctx.config` se presente, senão `loadConfigOrDeny(ctx.configPath)`) como defesa, sem gate novo.
  6. `decide()` **não** muda: assinatura `{gateFn, mode, ctx, env, logger}`; `DenyError` ⇒ deny (propaga); qualquer outro erro ⇒ allow + log `error` (`gate.js:161-177`).
  7. Seam de teste preservado: `toolInput.config` / `payloadObj.config` injetado pelo **host** (não pelo agente — o payload não vem de `args`) dispensa a carga de arquivo e o valor injetado é usado; com config ausente **e** sem injeção, vale o item 3.
  8. O `commands.suiteFull` e o selo sha256 do comando canônico **não** mudam (`harness.config.json:13-16`, `gate.js:120-135`): o deny novo é de config, não de comando selado.
- **Fora desta decisão**: o modo efetivo por gate (ADR-001); o schema e o veredito da contraproveva (ADR-003); o check da prosa de garantia (ADR-004); a forma do `harness.config.json` (inalterada); o `HARNESS_SEAL_JSON` e o fail-closed de selo ausente (`gate.js:753-764` — já é fail-closed e não muda).
- **Consequências se estiver errado**:
  - *Se o deny total for amplo demais e travar trabalho legítimo* (PRD §8 risco 1) ⇒ reversível em 1 PR: recuar para o deny lazy (reverter o bloco de carga) ou declarar uma lista de tools independentes do config. O custo do engano é um harness vermelho até a correção — daí a exigência de o `reason` ser acionável e o kill-switch ser a primeira saída.
  - *Se o `cause` enumerado for insuficiente para diagnosticar* ⇒ reversível: ampliar o enum (o loader passa a carregar um código de erro próprio) — 1 função + 1 teste; a mensagem do loader continua sendo a fonte para o operador.
  - *Efeito colateral já previsto*: os testes que hoje exercitam `ensureConfig`/`loadConfigOrDeny` como border mudam no mesmo diff (`.opencode/plugins/__tests__/config-dual-parity.spec.mjs`, `gate.spec.mjs`) — a suíte fica verde no mesmo PR.
  - *Nível de garantia declarado*: **🟢 garantido** para o caminho de deny (o `throw` é o primitivo de deny do runtime, `gate.js:161-177` e SPEC ADR-001) · **🟡 processo** para a hipótese de que o config sempre exista no host — o deny só dispara quando o config falta ou é inválido, e a restauração do config é operação do operador, não do agente.
